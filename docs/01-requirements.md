# 01 需求分析与验收标准

## 业务问题

内部员工需要查询制度或产品事实，但文档可能存在不同版本、冲突、缺失或临时不可用。如果系统直接拿检索结果拼接答案，会导致错误制度建议、没有依据的引用或模糊来源。因此目标不是只会回复问题，而是让一个模型在必要时主动检索/读取/复查，并对不确定结论给出清楚的状态。

## 输入、数据与用户

- 用户：合成员工，提出企业知识/产品事实类问题。
- 输入：`question: string`，可选多轮 `history: [{role,content}]`。
- 资料：`data/knowledge_base.json`，每条有 `id`, `title`, `version_date`, `scope`, `rule_key`, `rule_value`, `content`, `tags`。均为**虚构合成数据**。
- 工具：`search_documents(query)` 返回候选文档 ID/元数据；`read_document(doc_id)` 返回原文。
- 结果：回答、`doc_id`、逐字引文、资料缺口与明确任务状态，外加可观察的执行 Trace。

## 完成范围

| 验收点 | 用例 | 判断原则 |
| --- | --- | --- |
| 明确答案 | `01-clear` | 有引用，且先读原文；内容应与文档一致 |
| 文档冲突 | `02-conflict` | 引 D01/D02 两侧原文、揭示分歧并请求确认优先级 |
| 资料外问题 | `03-out-of-knowledge` | 返回 `insufficient_evidence`，不编造答案 |
| 改写后相似问题 | `04-paraphrase` | 口令/密码等表达变化仍可找到 D04 |
| 上下文追问 | `05-followup` | 结合前一问的“请假”语境理解“那还需要主管同意吗” |
| 工具失败 | `06` / `07` | 临时故障可恢复；连续故障不得谎称成功 |
| 动态动作路径 | `01` vs `02` vs `06` | 模型看到结果才选下一动作，Trace 可观察 |
| 文档改变 | `tests/test_agent.py` | 替换资料后最终答案也必须更新 |

## 非目标与约束

不接入真实公司系统、不调用真实内部知识库、不做上线部署，不承诺生产级权限、可用性、语义正确性或合规认证。无需 GUI、Multi-Agent 或大型运行框架。Python 标准库与本地 Mock 工具用于减少部署成本。模型不可用时可演示控制流，但**Mock 输出不能证明真实模型达标**。

## 成功标准

最小可运行：CLI、可复现测试、6 项验收点、至少 3 组真实执行记录、明确资源限制与错误返回、所需交付文档。真实性标准：实际生产模型的动作由 API 返回 JSON，而不是写死后伪装为模型输出；真实模型测试数据应单独保存到 `examples/traces/live/`。
