# 05 复盘：工程困难、收获与下一步

## 已观察到的项目问题

1. **工具调用 ≠ 模型决策**。固定搜索和固定读取序列即使调用了大模型来润色答案，也不是题目要求的“观察后决定下一步”。为此系统将下一动作明确作为模型输出，执行器只执行/校验；另外用 `MockPlanner` 做离线回归，并在输出中明确标记它并非真正的模型自主决策。
2. **有原文不等于答案可信**。冲突例子中的 D01/D02 都是合法原文，但共同出现时不能凭日期替用户确定哪个制度有效，因此必须显示相反的引文，避免无依据选择。
3. **异常状态不能包装成成功**。工具实际报错时要在 Trace 中保存错误，保留 `tool_failure` / `incomplete_*` 等状态，而不能靠一句“完成”掩盖失败。

## 工程学习与设计取舍

这版原型把“搜索候选”“获取证据”“决定动作”“校验回答”拆成独立职责，并用一次故障注入和资料原文替换检验行为确实与观察相关。原生 Python + CLI 相比复杂框架更容易定位问题，但丢失了成熟框架的状态持久化、可视化、重试策略及生产级工具审计功能。

## 下一步改进（按优先级）

1. 真实 LLM 的路径及异常验收，量化结果并分析至少一个失败案例；这是正式交付前最重要的待完成项。
2. 搜索替换为 BM25/embedding 的混合检索与 cross-encoder reranker，测不同问法的召回率、延迟和成本。
3. 为文档增加 `effective_from`, `supersedes`, `applicability`, `source_authority` 字段，使用显式版本关系而非“最新即正确”的假设。
4. 引入答案与引文的语义蕴含验证；对仍存争议的规则做人工确认。
5. 若未来接入真实企业数据，补齐权限隔离、敏感信息过滤、提示注入防御和日志脱敏。
